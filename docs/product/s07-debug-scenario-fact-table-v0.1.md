## 1. 场景目标

调试人员要验证：

> 指定烧杯和粉桶能否被安全地准备到 S07，并按目标质量完成投粉；如果中间出现等待、物理动作结果未知、物料账本未提交或设备前置条件不满足，调试人员能够判断原因并采取安全的下一步动作。

## 3. 中断路径事实表

| 中断 | 实际含义 | 用户必须看到 | 错误的简化 | 正确的下一步 |
| --- | --- | --- | --- | --- |
| 机器人被另一分支占用 | 不是设备故障，是共享执行器互斥 | 当前占用节点、等待节点、预计释放依据 | 显示“节点等待” | 查看占用链，等待或处理占用节点 |
| 来源 Site / 目标 Site 见证失败 | 物理位置无法确认 | 哪个 Site、哪条见证、最后一次读数和时间 | 显示“转运失败” | 现场核验、重新读取见证或转人工处理 |
| 物理放料成功，Host 记账失败 | 实物可能已经移动，但系统账本未更新 | pick / place 成功证据、Host 调用结果、当前账本状态 | 允许自动重试转运 | 禁止重发；进入物料人工对账 |
| 命令变为 `UNKNOWN` | 设备可能执行过，也可能没有执行 | `command_id`、`boot_id`、最后命令输出、现场见证 | 当成普通失败并重试 | `reconcile`，或确认设备安全后人工取消 |
| 存在未对账 UNKNOWN | 后续机器人动作被安全阻断 | 哪些命令阻断派发、阻断范围 | 显示“机器人离线” | 先完成对账，解除运动阻断 |
| `target_mass_g` 非法 | 输入不满足 `(0, 100] g` | 实际输入、约束、影响节点 | 统一显示提交失败 | 修正输入后重新做准入检查 |
| 粗粉桶和精粉桶占用同一 Site | 运行参数和设备位置冲突 | 两个粉桶的 Site、冲突规则 | 只显示设备动作失败 | 更换 Site / 物料绑定 |
| 投粉成功但 balance history 写入失败 | 工艺可能完成，证据记录不完整 | 动作结果、最终质量、历史记录错误 | 把运行标成失败 | 保留成功事实，同时标记证据缺失 |

## 4. 从事实表得到的调试要求

这条真实路径说明，运行页面至少需要同时组织五类事实：

1. **意图事实**：工作流版本、运行输入、仿真 / 真机。
2. **依赖事实**：物料实例、Warehouse、Site、设备占用和下游准入条件。
3. **执行事实**：NodeJob、设备动作阶段、命令 ID、PLC / 传感器见证。
4. **账本事实**：物理位置与 Host 物料记录是否一致。
5. **处置事实**：当前允许重试、对账、人工取消、等待或继续中的哪一种动作。

这些事实不能被压成一个总状态。至少要能区分：

```text
运行逻辑状态
设备命令状态
物料物理状态
Host 账本状态
证据完整性状态
```

## 5. 本场景暂时不做的事情

- 不根据 S07 直接决定首页有几个入口；
- 不把每个 PLC 变量都展示给用户；
- 不把所有设备动作都做成独立页面；
- 不把 `UNKNOWN`、账本失败和普通动作失败统一设计成同一种异常弹窗；
- 不先决定用 DAG、矩阵还是时间轴，而是先保证事实关系能被表达。

## 6. 需要业务确认的三个问题

1. 当物理放料成功但 Host 记账失败时，谁负责现场对账，调试人员能否直接发起对账？
2. S07 投粉完成的最终事实以 PLC 天平读数、动作返回值，还是二者组合为准？
3. 仿真环境是否也要模拟 `UNKNOWN`、机器人互斥和 Host 记账失败，还是只模拟成功路径？
