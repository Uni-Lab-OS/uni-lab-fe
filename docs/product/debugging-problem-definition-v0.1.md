# Uni-Lab 调试场景问题定义 v0.1

> 这份文档只定义问题，不确定首页、导航和组件方案。
>
> 参考：`Uni-Lab-OS/frontend`、`packages/core` 当前场景实现、
> `/Users/dp/Downloads/experiment-debug-platform.html`。

## 1. 我们讨论的“调试”是什么

这里的调试不是查看设备状态，也不是浏览任务列表。它是一个反复确认和收敛的过程：

> 调试人员要验证某个已确定版本的实验定义，在指定环境和资源条件下能否按预期执行；如果不能，要定位阻断原因，采取可解释的处理动作，再继续验证。

因此，一次调试工作的最小认知单位不是“设备”“物料”或“任务”，而是：

```text
一个定义版本
  + 一组本次运行输入和资源绑定
  + 一个仿真 / 真机环境
  + 一次运行及其所有节点证据
```

调试人员始终在回答四个问题：

1. **我现在在验证什么？** 工作流 / 实验操作 / 设备动作的哪个版本？
2. **它现在能不能运行？** 哪些输入、设备、物料、试剂、库位或连接条件阻断了运行？
3. **它现在运行到哪里？** 哪些节点已完成、正在执行、并行等待、结果未知或需要人工处理？
4. **我下一步能做什么？** 修改输入、选择资源、运行 Preflight、单步、继续、重试、人工确认、结算或停止？

如果页面不能连续回答这四个问题，调试人员就会依靠猜测、跨页面比对和记忆来操作。

## 2. 核心问题陈述

当前产品把系统按领域对象和后端能力拆开了，但调试人员是按“一次运行的问题”来工作的。定义、资源、运行状态和处置动作分散在不同页面；每个页面又同时承担浏览、编辑、执行和异常处理。

结果是：

> 用户看到了很多信息，却无法在当前上下文中判断“这次调试是否可以继续、为什么不能继续、下一步应该执行哪个动作，以及这个判断由什么证据支持”。

这是当前最核心的问题。页面数量、颜色、画布布局和字段数量都是它的表现，不是问题本身。

## 3. 问题一：调试上下文无法建立

### 现象

- 原型把“设备动作、实验操作调试、工作流调试、实验任务”并列放在调试导航中，资源又有单独的公共中心。
- OS 前端的工作流、实验操作、设备动作和任务页面都可以成为入口，但入口没有明确说明用户是在“定义、准备、运行还是处置”。
- 用户打开页面后，首先面对的是模块名称，而不是当前要验证的目标和当前运行上下文。

### 根因

导航按对象和实现模块组织，调试工作却按意图组织。用户需要的是“开始一次验证”或“继续处理一次运行”，系统给出的是多个平级模块。

### 后果

- 新建调试、恢复已有运行、隔离设备问题三种不同任务混在一起。
- 用户不知道应该从工作流、设备还是任务进入。
- 用户在不同入口间跳转后容易丢失版本、输入、资源和节点上下文。

## 4. 问题二：无法形成“运行是否可行”的单一判断

### 现象

- 工作流页面有输入合同、物料绑定和 Preflight。
- 设备页面有在线、动作能力和运行时状态。
- 物料页面有库位、占用和使用关系。
- 试剂页面又区分目录、容器库存、历史和分装。
- 这些信息分别有价值，但用户看不到一份以“本次运行”为中心的准备结论。

### 根因

资源事实和运行准入判断没有形成清晰的层级：资源页面提供事实，Preflight 提供准入判断，运行准备又需要让用户做本次选择。当前界面容易把三者混成“前端自己拼一个可运行状态”。

### 后果

- 用户不知道某个资源是“当前不可用”“本次未选择”还是“服务端尚未判断”。
- 缺少资源时只能回资源页面查找，回来后还要重新确认原运行上下文。
- 页面越展示更多资源字段，反而越难回答“现在能不能跑”。

## 5. 问题三：定义和执行的边界不清楚

### 现象

- 原型的实验操作和工作流页面同时出现库、流程树、画布、节点检查器、保存 / 发布和运行调试。
- 工作流运行后，同一画布又出现下一步、继续、暂停、受控停止、检查点恢复和补偿路径。
- OS 前端虽然已经区分 draft、published revision、Task 和 NodeJob，但页面仍把拓扑查看、定义编辑和运行观察放在同一个工作区中。

### 根因

定义回答“应该怎么执行”；运行回答“这一次实际发生了什么”。两者共享节点结构，但生命周期、可变性、版本和操作权限不同。

### 后果

- 用户不清楚当前修改会不会影响正在运行的任务。
- 用户把运行时参数、定义参数和本次输入混为一谈。
- 失败时不知道应该修改定义、修改运行输入，还是处理现场状态。

## 6. 问题四：并行运行的结构、状态和时间无法同时理解

### 现象

- DAG 能表达依赖和分支，但不直接表达多个 Task 当前各自运行到哪里。
- 任务矩阵能表达多个 Task 和节点状态，但不直接表达单个工作流的因果结构。
- Timeline / 甘特图能表达时间，却容易让用户把“时间先后”误认为“依赖关系”。
- 原型把任务排程、节点时间段、运行状态和异常处置放在同一任务页面中。

### 根因

结构视图、运行状态视图、时间事件视图没有明确分工，也没有明确哪个视图是当前操作的主视图。

### 后果

- 用户无法快速回答“现在有哪些节点同时活动、哪个节点阻断了下游”。
- 并行节点的 input / output / feedback 难以逐一定位。
- 发生异常时，用户容易只看到一个总体失败状态，而看不到实际阻断链路。

## 7. 问题五：状态、命令和结果的语义不一致

### 现象

- “开发模式 / 生成模式”“调试模式 / 生产模式”“自动运行 / 单步运行”混在一起。
- 任务控制包括暂停、继续、单步、取消、受控停止，但命令提交后并不等于状态已经生效。
- 节点可能处于失败、结果未知、人工确认、等待资源、执行锁未释放、物料结算未完成等不同状态。

### 根因

环境、调度方式、业务状态、控制意图和物理处置状态没有在界面上分层表达。

### 后果

- 用户误以为点击“暂停”后设备已经安全停止。
- 用户误以为“失败”可以直接重试，忽略结果未知和现场核验。
- 用户不知道当前按钮是在发出命令、等待权威状态，还是已经完成动作。

## 8. 问题六：资源详情的展示没有围绕调试决策收敛

### 现象

- 物料容易陷入几何、层级、容器、容量、库位和占用信息的全量展示。
- 设备同时展示台账、模板、动作能力、连接、运行时状态和最近结果。
- 试剂同时涉及 CAS 目录、具体库存、供应商、浓度、物性、容器和历史。
- 原型和 OS 都提供了很多真实能力，但这些能力常常以完整管理页形式出现。

### 根因

资源对象本身是长期管理对象；调试只需要其中与当前运行判断和处置相关的事实。系统没有清楚区分“资源事实”“本次运行引用”和“资源维护动作”。

### 后果

- 用户在详情中看到了大量字段，却找不到当前状态和当前影响。
- 同一个资源在运行准备、运行节点和资源管理页中被重复解释。
- 资源的维护动作容易被误认为是运行中的临时操作。

## 9. 问题七：对象层级和产品语言不符合用户心智

当前真实层级是：

```text
设备动作 → 实验操作 → 工作流 → Task / Run → NodeJob
```

但界面容易把它们呈现为并列模块。用户因此难以理解：

- 实验操作是可复用定义，还是一次运行？
- Task 是实验任务、一次运行，还是排程记录？
- NodeJob 是工作流节点定义，还是这次节点的执行实例？
- 设备动作调试和工作流调试为什么最终都要回到同一套 Job 状态？

这个问题不是单纯换几个中文名称就能解决，需要在页面结构中表现“定义层”和“运行层”的关系。

## 10. 将问题收敛为三个体验断点

前面的七个问题可以归并为三个需要验证的体验断点：

### 断点 A：进入调试时不知道从哪里开始

用户无法在进入系统的第一步明确自己的意图：启动新运行、恢复活动运行，还是隔离设备问题。

### 断点 B：运行前后不知道当前事实是否足够支持下一步

运行准备时不知道资源和输入是否真的满足准入；运行中不知道当前状态、阻断原因和证据是否足够支持继续、重试或停止。

### 断点 C：有动作可点，但不知道动作的后果和完成条件

按钮、状态和证据之间没有形成闭环。用户知道“可以点什么”，却不知道点击后系统正在等待什么、现场需要确认什么、什么事实出现后才算完成。

这三个断点比“首页应该有几个分类”更优先。只要断点没有解决，换成四个、五个或七个一级入口都可能重新产生混乱。

## 11. 当前问题的边界

### 本轮要解决

- 一次调试运行的目标、上下文和生命周期如何被用户理解；
- 运行前的输入、资源选择和 Preflight 如何形成一份可解释的准备结论；
- 运行中的结构、并行状态、节点证据和处置动作如何形成闭环；
- 定义、运行、资源事实和资源维护之间如何分层；
- 仿真 / 真机、自动 / 单步、命令提交 / 状态生效如何分开表达。

### 本轮暂不解决

- 首页具体采用几张卡片、几个导航入口；
- 完整工作流编辑器的交互细节；
- 生产排程、自动排产和生产审批；
- 所有资源对象的完整后台管理；
- 颜色、图标、画布皮肤和视觉风格。

## 12. 在进入信息架构前必须验证的场景

先用同一条真实工作流走通以下三个场景，不急于画首页：

1. **从零开始调试**：选择一个已发布工作流版本，填写输入，选择资源，发现一个 Preflight 阻断并完成修正，然后启动仿真。
2. **运行中定位问题**：两个节点并行，其中一个等待资源、另一个返回异常；用户需要知道先处理什么，并查看两个节点各自的 input / output / feedback。
3. **结果不确定后的处置**：设备动作命令已提交但结果未知；用户需要查看证据、确认现场、选择重试 / 继续 / 停止，并知道何时资源锁和物料状态完成结算。

每个场景只记录四件事：用户当时想回答的问题、需要看到的事实、可以采取的动作、动作完成的确认条件。完成这一步后，才有足够依据决定哪些内容应该成为页面、抽屉、节点详情或二级入口。

## 13. 用真实 SZLab 工作流校正问题定义

### 13.1 S07 不是“两个设备动作”，而是一条带并行和物料账本的运行

真实工作流 `S07 粉桶与烧杯搬运后固体称量` 只有一个最终目标：把指定粉桶和烧杯准备到 S07，然后按目标质量完成投粉。但它在运行上包含：

```text
并行准备
  ├─ 烧杯：s3_unused_beaker / L1B1 → s07_process_warehouse / S0722
  └─ 粉桶：准备 P01 → powder_container_warehouse / L1C1 → S07 / P01
        ↓
S07 使用烧杯 + 粉桶完成 dose_powder_with_materials
```

两个分支都使用 `szlab_mixer_robot`，所以逻辑上可以并行，物理上又要竞争同一个机器人。调试人员需要同时理解：

- 哪些节点满足依赖、哪些节点正在等待机器人互斥；
- 烧杯和粉桶当前分别在哪个 Warehouse / Site；
- P01 是粉桶的设备位置，不是普通文本参数；
- 两次转运成功后，Host 的物料归属是否已经记账；
- 只有两个准备分支都完成，S07 投粉节点才有资格开始。

这说明“并行任务状态”不能只显示一组颜色，也不能只把节点排成时间轴。用户要看到的是 **分支状态 + 共享设备冲突 + 物料位置事实 + 下游准入关系**。

### 13.2 一次物料转运包含三个不同的事实阶段

`transfer_material_atomic` 不是一个不可分解的黑盒动作，它依次执行：

```text
机器人取料
  → 机器人放料
  → Host transfer_resource 记账
```

真实驱动明确规定：物理放料完成但 Host 记账失败时，不能自动重做搬运，必须转人工对账。因而页面至少需要区分：

1. 物理动作是否完成；
2. 物料现场是否已经处于目标 Site；
3. 系统库存账本是否已经提交成功；
4. 当前是否允许继续下游节点。

把这些事实压成一个“转运失败”会直接诱导错误重试。

### 13.3 UNKNOWN 是调试中的核心状态，不是普通异常

SZLab 机器人命令账本会持久化 `command_id`、请求指纹、`boot_id` 和命令状态。真实状态包括：

```text
ACCEPTED / RUNNING / SUCCEEDED / FAILED / CANCELED / UNKNOWN / REJECTED
```

驱动重启后，之前仍在途的命令会被标记为 `UNKNOWN`；存在未对账的 UNKNOWN 时，新的机器人运动会被拒绝。用户必须先查看命令证据，通过 `reconcile` 重新读取现场见证，或者在确认设备安全空闲后提交带理由的人工取消。

因此调试界面真正要表达的不是“失败后点重试”，而是：

```text
命令结果未知
  → 查看最后已知命令、设备启动批次、物料和库位见证
  → 对账成功，或人工确认取消
  → 系统解除后续运动阻断
```

这也是为什么“命令已提交”“设备已停止”“结果已确认”“资源已解锁”必须是四个不同的事实。

### 13.4 设备在线不等于动作可执行

真实设备动作还会检查具体的物理前置条件。例如 S04 磁搅动作会等待：

- 对应位置有物料；
- 工位处于空闲状态；
- PLC 允许加工；
- 参数写入成功；
- 加工完成信号出现；
- 加工后物料在位验证成功。

机器人动作还可能检查来源 / 目标 Site 在位、夹爪负载、运动许可、程序版本、点位版本和未对账命令。页面只显示“设备在线 / 离线”无法帮助用户判断动作为什么不能开始。

### 13.5 真实样本揭示的最终问题

结合 S07 以及更长的“单样品原子流程”，当前产品真正需要解决的是：

> 调试人员无法沿着一次真实运行，从工作流意图一路追踪到设备命令、物料 Site、Host 账本和下游准入，并在发生等待、未知或部分成功时知道下一步安全动作。

这比“工作流页面太复杂”更精确。复杂度来自运行事实之间的因果关系，而不是节点数量本身。

更长的 `SZLab 单样品原子流程` 把这个问题放大：测试契约明确它包含 8 个 `material_source`，14 次标准物料转运、1 次原子取料倒液放料，并且至少有两路 S06 溶剂各 10 mL、S09 液体试剂 0.5 mL 的库存需求。对调试人员而言，这不是“看一张更大的 DAG”，而是要知道每一条物料链、库存需求和共享设备约束在当前运行中的作用。

### 13.6 对问题定义的新增验收条件

用 S07 作为首个真实样本时，任何候选 UI 方案都必须能让用户回答：

1. 烧杯搬运和粉桶搬运当前各处于哪一阶段？
2. 它们是在等待机器人、等待 Site / 物料，还是已经进入设备动作？
3. 物理放料成功后，Host 账本是否已提交？
4. 为什么 S07 投粉还不能开始？
5. 如果机器人命令变成 UNKNOWN，当前允许执行哪些动作，哪些动作被禁止？
6. 目标质量、粉桶、烧杯和 P01 的真实输入与最终输出是什么？

如果方案只能回答“哪个节点红了”，就还没有解决真实调试问题。
