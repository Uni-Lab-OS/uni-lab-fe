# Uni-Lab 调试任务流 v0.1

> 本文完成调试产品设计的第五步：把问题定义和运行时模型转成可以实际走通的调试任务流。
>
> 三条任务流都以真实 SZLab 运行语义为依据，不提前规定页面数量、导航位置或具体组件。

## 1. 三条任务流的共同约束

三条流都围绕同一个 `DebugRunContext` 展开：

```text
已发布定义修订
  + 本次输入和资源绑定
  + 仿真 / 真机环境
  + Preflight 报告
  + Task / NodeJob / Attempt
  + 设备、物料、账本和证据
  + 当前允许的处置动作
```

三条流必须遵守以下规则：

1. **运行身份不丢失**：从定义、准备、运行到处置，始终保留 workflow revision、Task、NodeJob、Attempt 和 Command 身份。
2. **配置和事实分开**：提交前的输入和绑定是可编辑草稿；SubmitRun 后使用的输入、版本和环境冻结为运行事实。
3. **Preflight 是准入权威**：前端可以做字段级提示，但不能把设备、物料和库存的局部查询拼成“可运行”。
4. **并行按分支和资源同时观察**：逻辑上可并行的分支可能因共享机器人、工位或锁而物理串行。
5. **结果未知不能重试**：`execution_unknown`、现场见证冲突、物理放料成功但 Host 记账失败，都必须进入核对或人工处置。
6. **命令完成和动作完成分开**：命令提交、控制状态生效、设备动作完成、账本结算完成是不同确认点。
7. **每一步都有完成条件**：按钮点击本身不算任务完成，只有对应事实和证据到达后才算完成。

## 2. 任务流一：从零开始调试

### 2.1 目标和触发

**目标**：从一个已发布工作流修订开始，完成本次运行的输入和资源绑定，通过 Preflight，并创建一条可观察的 Task。

**典型样本**：S07 固体投粉；用户选择目标质量、烧杯、粉桶、S07 设备和仿真 / 真机环境。

**触发**：用户选择“开始调试”，或从最近工作流恢复尚未提交的 Run Configuration 草稿。

**开始前必须知道**：

- 将要验证的工作流名称和 Published Revision；
- 本次环境是仿真还是真机；
- 工作流需要哪些输入、物料、试剂、设备和库位；
- 提交后会创建一条 Task，不会修改工作流定义。

### 2.2 主路径

| 步骤 | 用户要回答的问题 | 系统必须提供的事实 | 用户动作 | 完成条件 |
| --- | --- | --- | --- | --- |
| 1. 选择定义 | 我究竟在验证哪一版？ | 工作流名称、Revision、发布状态、最近变更摘要、流程结构预览 | 选择已发布修订 | Revision 身份冻结到当前草稿 |
| 2. 选择环境 | 在仿真还是真机上验证？ | 环境类型、连接状态、数据新鲜度、环境能力说明 | 选择仿真 / 真机 | 环境成为 Run Configuration 的显式字段 |
| 3. 填写输入 | 这次运行的目标是什么？ | 必填输入、范围、单位、默认值、对下游节点的影响 | 填写输入，如 `target_mass_g` 和 `recipe_name` | 输入通过本地格式校验并保存到草稿 |
| 4. 绑定资源 | 这次具体使用哪些物料和设备？ | 候选实例、显示名、条码 / 批次、来源 Warehouse / Site、状态、余量、占用和绑定原因 | 选择资源候选 | 每个必需 ResourceSlot 都有稳定绑定或明确缺口 |
| 5. 运行 Preflight | 现在为什么能跑或不能跑？ | OS 检查报告、检查组、状态、原因码、阻断节点、详情和更新时间 | 执行 Preflight | 报告生成，所有问题有可追踪的检查项 |
| 6. 处理检查项 | 哪些问题需要修改，哪些只是等待或确认？ | `passed / blocked / deferred / confirmation_required`，对应输入 / 资源 / 节点 / 设备 | 点击检查项定位到字段或资源；修改草稿；必要时确认 | 阻断项清除，或用户明确知道仍需等待 / 确认 |
| 7. 再次 Preflight | 修改后的事实是否仍然有效？ | 新的 `checked_at`、报告状态、报告内容变化 | 重新运行 Preflight | 旧报告不再被当成当前准入依据 |
| 8. 提交运行 | 我是否要创建这次 Task？ | 冻结的 Revision、输入、绑定、环境、运行模式和风险提示 | 确认并 SubmitRun | OS 接受请求并返回 Task 身份，或返回明确拒绝 |
| 9. 进入运行观察 | 任务是否已经开始，当前需要关注什么？ | Task 生命周期、控制状态、NodeJob 摘要、首个注意事项、更新时间 | 打开运行详情 | 用户能回答“这次运行是什么、现在在哪里、下一步是什么” |

### 2.3 准入分支

| 分支 | 实际含义 | 用户下一步 | 不能做的简化 |
| --- | --- | --- | --- |
| 输入 `blocked` | 值不满足合同，例如 `target_mass_g <= 0` 或超过上限 | 修改输入，重新 Preflight | 只显示“提交失败” |
| 资源候选缺失 | 没有满足模板、Site、数量或状态的实例 | 更换候选、补充资源或退出准备 | 把空列表解释成设备离线 |
| 设备 / Claim `deferred` | 当前报告无法确定运行时占用或调度结果 | 显示“提交时再确认”，提交仍由 OS 再次准入 | 前端自行宣布已可运行 |
| `confirmation_required` | 需要用户确认风险、现场条件或特殊绑定 | 查看原因并显式确认 | 把警告自动当成通过 |
| 选择未映射 | UI 显示了资源选择，但 OS 合同没有明确接收字段 | 阻止提交并提示映射缺口 | 把选择偷偷塞进任意 `input` |
| SubmitRun 网络结果未知 | 请求是否创建 Task 无法确认 | 用幂等身份查询或刷新 Task 事实；冻结原草稿 | 盲目再次提交，可能重复物理任务 |

### 2.4 完成判定

这条流完成，不是因为“开始调试”按钮被点击，而是因为：

- 已返回可追踪的 Task 身份；
- Task 绑定的 Revision、输入、环境和资源选择已冻结；
- 用户能看到 Task 当前生命周期和控制状态；
- 首个可执行、等待或阻断的 NodeJob 有原因和证据入口；
- 若提交结果未知，系统已进入查询 / 对账路径而不是重复提交。

## 3. 任务流二：运行中定位问题

### 3.1 目标和触发

**目标**：在一个已有 Task 中，定位当前真正阻断运行的节点或资源，判断应等待、查看证据、重试、暂停、单步、继续还是升级人工处置。

**典型样本**：S07 两条搬运分支逻辑并行；粉桶准备或转运异常，烧杯分支仍在等待共享机器人；用户需要先处理真正阻断下游的原因。

**触发**：

- 用户打开活动运行；
- 运行列表出现新的注意事项；
- 收到运行失效通知后重新读取 Task / Jobs；
- 用户从节点、资源或设备上下文返回当前 Task。

### 3.2 主路径

| 步骤 | 用户要回答的问题 | 系统必须提供的事实 | 用户动作 | 完成条件 |
| --- | --- | --- | --- | --- |
| 1. 恢复运行上下文 | 这条运行的目标、版本和环境是什么？ | Task、Revision、输入摘要、仿真 / 真机、控制和清理状态 | 打开运行 | 上下文与上次离开时一致，状态已重新读取 |
| 2. 看当前关注点 | 现在最需要处理什么？ | 关注状态、阻断范围、更新时间、连接 / 新鲜度 | 查看关注摘要 | 关注点能追溯到原始状态和原因码 |
| 3. 查看活动节点集合 | 哪些分支在运行、等待或需要处理？ | 所有当前 NodeJob、分支、attempt、waitReason、共享资源占用 | 选择一个或多个活动节点 | 不把并行运行压成唯一“当前节点” |
| 4. 定位阻断链 | 哪个事实让下游不能开始？ | `blockedBy`：结构、物料、Site、Claim、设备能力、证据或结算 | 从阻断项跳到来源节点 / 资源 / 命令 | 选出可操作的首个阻断点 |
| 5. 读取节点证据 | 这个节点到底发生了什么？ | 当前 attempt 的 input、dispatch、命令、设备反馈、output、错误、时间和历史 attempt | 打开 NodeJob 详情 | 用户能区分等待、失败、未知和部分成功 |
| 6. 判断处置类型 | 我应该等待、修复、重试还是停止？ | OS 返回的动作能力、前置条件、影响范围、完成条件 | 选择允许的动作 | 动作与事实匹配，危险动作有确认 |
| 7. 执行控制 / 处置 | 动作是否已经生效？ | 命令 ID、幂等键、`pending / succeeded / rejected`、控制状态变化 | 发送命令或完成人工确认 | 不能把命令提交直接显示成动作完成 |
| 8. 重新读取运行 | 处理后下游是否解除阻断？ | 更新后的 Task / Job / Event / Feedback、Claim、Site、账本和清理事实 | 等待失效通知或主动刷新 | 阻断链重新计算，下一步动作明确 |

### 3.3 并行定位规则

运行中定位必须同时保留三种关系：

```text
工作流结构：烧杯分支 ─┐
                       ├─→ S07 投粉
粉桶分支   ────────────┘

共享资源关系：烧杯转运 ─┐
                        ├─→ szlab_mixer_robot Claim
粉桶转运   ─────────────┘

时间关系：谁先获得 Claim、谁正在运行、谁在等待、谁已经完成
```

因此：

- 一个分支等待机器人，不等于它失败；
- 另一个分支失败，不等于整个 Task 的所有节点都失败；
- 结构上已满足依赖，不等于共享设备已经可派发；
- Timeline 只能补充发生顺序，不能替代结构和阻断关系。

### 3.4 定位分支

| 观察结果 | 判断 | 用户动作 | 完成条件 |
| --- | --- | --- | --- |
| `waiting`，原因是共享 Claim | 资源互斥，不是动作失败 | 查看占用节点和释放依据；等待或处理占用节点 | Claim 释放，或出现新的阻断 |
| `waiting`，原因是上游 NodeJob | 结构依赖未完成 | 打开上游节点，沿证据链定位 | 上游成功并满足下游准入 |
| `failed`，且资源现场未变化 | 已确认失败，可能允许重试 | 查看失败证据、检查重试前置条件 | 新 attempt 创建，或明确放弃 / 取消 |
| `execution_unknown` | 不能确认动作是否执行 | 转到任务流三，冻结原命令身份 | 对账或人工取消完成 |
| `succeeded`，但证据 `partial` | 工艺可能完成，证明链不完整 | 查看缺失证据和业务规则 | 补齐证据，或明确标记为待处理 |
| NodeJob 已成功但下游仍阻断 | 可能是 Site、账本、库存或结算未收敛 | 查看 `blockedBy` 和资源事实 | 资源事实收敛后重新准入 |

### 3.5 完成判定

这条流完成，不是因为某个节点变绿，而是因为：

- 当前阻断点已经被定位到具体事实、来源 ID 和原因码；
- 用户知道是等待、修复、重试、对账、人工确认、继续还是停止；
- 已执行的动作有命令身份和生效确认；
- 运行模型重新读取后，活动节点和下游准入关系发生了可解释变化；
- 若问题无法在当前上下文安全解决，Task 已进入明确的人工处置或受控停止状态。

## 4. 任务流三：未知结果后的处置

### 4.1 目标和触发

**目标**：在物理动作是否发生无法确认，或实物已移动但 Host 账本未提交时，避免重复执行，完成现场核对、账本处理和后续运行决策。

**典型样本**：机器人命令因重启变为 `UNKNOWN`；或者 `transfer_material_atomic` 的物理放料成功但 `transfer_resource` 失败。

**触发**：

- NodeJob / DeviceCommand 返回 `execution_unknown`；
- 驱动启动恢复把在途命令标记为 `UNKNOWN`；
- 物理放料见证成功，但 Host 记账失败；
- Site 见证与账本记录冲突；
- 新运动因未对账 UNKNOWN 被安全阻断。

### 4.2 主路径

| 步骤 | 用户要回答的问题 | 系统必须提供的事实 | 用户动作 | 完成条件 |
| --- | --- | --- | --- | --- |
| 1. 冻结动作身份 | 哪个物理动作可能重复？ | Task、NodeJob、Attempt、Command ID、请求指纹、设备、参数和提交时间 | 查看原始动作详情 | 原始命令被标记为不可盲目重发 |
| 2. 查看最后已知证据 | 设备、物料和账本最后分别知道什么？ | `boot_id`、最后响应、pick / place 状态、Site 见证、传感器、Host ledger 结果、时间新鲜度 | 展开证据包 | 物理事实和系统事实分开可见 |
| 3. 确认阻断范围 | 哪些后续动作被禁止？ | 未对账命令、受影响设备、物料、Site、下游 NodeJob 和 Claim | 查看阻断链 | 用户知道是单节点、单设备还是整条运行被阻断 |
| 4. 现场核验 | 现场物料到底在哪里，设备是否安全？ | 所需现场检查项、最后读数、检查人和时间 | 由有权限人员完成现场核验 | 有明确的现场确认记录，或记录为无法确认 |
| 5. 尝试对账 | 能否通过权威见证确定结果？ | `reconcile` 能力、读取到的 Site / 设备见证和对账结果 | 发起对账 | UNKNOWN 被解析为成功、失败或仍未知 |
| 6. 无法执行时人工取消 | 设备已确认安全且动作未完成吗？ | 人工取消前置条件、风险提示、理由、操作人 | 提交带理由的 `resolve_unknown_as_canceled` | 原命令被明确取消，审计信息完整 |
| 7. 处理物料账本 | 实物和 Host 记录是否一致？ | 当前物理位置、目标 Site、Host 记录、库存 / 预留和冲突 | 发起人工物料对账或等待授权 | 账本事实与现场事实达成一致，或进入人工升级 |
| 8. 解除下游阻断 | 后续动作现在是否安全可执行？ | 更新后的 Command、Resource、Site、Claim、NodeJob 准入和清理状态 | 继续、恢复、重新 Preflight 或受控停止 | OS 重新允许下游派发，或明确停止路径 |

### 4.3 两类未知结果必须分开

#### A. 命令结果未知

```text
UNKNOWN
  → 读取 command / boot / device witness
  → reconcile
      ├─ 确认成功 → 更新资源事实和下游准入
      ├─ 确认失败 → 按失败路径评估 retry
      └─ 仍然未知 → 现场安全确认 / 人工取消 / 升级
```

在 `UNKNOWN` 未解除前：

- 禁止盲目再次派发同一物理动作；
- 不得把设备在线显示成动作可执行；
- 不得直接释放可能仍被占用的 Claim；
- 下游节点继续显示明确的阻断范围。

#### B. 物理动作成功、Host 账本失败

```text
pick 成功 → place 成功 → Host transfer_resource 失败
                         ↓
                  物理位置可能已改变
                         ↓
                   人工物料对账
                         ↓
              更新账本 / 记录冲突 / 解除下游阻断
```

这条路径不能使用普通 `retry transfer`，因为再次搬运可能造成重复移动或错误库存。页面要明确显示：

- 物理放料证据；
- Host 账本调用结果；
- 当前账本是否可信；
- 物料下一步允许的对账动作；
- 在对账完成前哪些节点被阻断。

### 4.4 处置分支

| 分支 | 允许动作 | 结束状态 |
| --- | --- | --- |
| 对账确认成功 | 更新命令 / Site / 物料事实，重新检查下游 | 运行可继续，或进入新的明确阻断 |
| 对账确认失败 | 记录已确认失败，按失败策略决定 retry / cancel | 失败已知，不再是 UNKNOWN |
| 现场安全但动作未发生 | 带理由人工取消原命令 | 运动阻断解除，物料状态按事实处理 |
| 现场仍无法确认 | 保持 UNKNOWN，升级人工或受控停止 | 运行保持待核对，不允许自动继续 |
| 物理事实与账本冲突 | 人工物料对账，不重发机器人动作 | 账本一致或进入差异处置 |
| 下游已有不可逆动作 | 先评估影响范围和补偿路径 | 继续、补偿或受控停止由 OS / 业务规则决定 |

### 4.5 完成判定

这条流完成必须同时满足：

- 原始命令的结果已变为明确成功、明确失败或明确人工取消；
- 物理位置、Host 账本和库存 / 预留的差异已处理或被明确升级；
- 受影响的 Claim、设备运动阻断和下游 NodeJob 准入已重新读取；
- 所有人工确认包含操作人、时间、理由和关联身份；
- 用户明确知道运行是继续、重试、停止还是等待进一步处理。

## 5. 三条任务流之间的衔接

```text
从零开始调试
  → Task 已创建
  → 运行中定位问题
      ├─ 无阻断 → 继续观察直到收敛
      ├─ 已知失败 → 处置 / 重试 / 停止
      └─ UNKNOWN 或账本冲突 → 未知结果处置
                              ├─ 已解决 → 返回运行中定位
                              └─ 无法解决 → 人工处置 / 受控停止
```

三条流共享同一套身份和证据，但入口问题不同：

| 任务流 | 用户当前问题 | 主要事实 | 主要完成条件 |
| --- | --- | --- | --- |
| 从零开始 | 这次运行是否具备开始条件？ | Revision、输入、绑定、Preflight | Task 身份已创建并可观察 |
| 运行中定位 | 当前哪里阻断了运行，下一步是什么？ | NodeJob、分支、Claim、`blockedBy`、证据 | 阻断已处理或进入明确处置 |
| 未知结果处置 | 物理动作到底发生了吗，能否安全继续？ | Command、现场见证、账本、人工记录 | 结果和账本明确，阻断重新评估 |

## 6. 任务流验收标准

任何候选 UI 方案都必须能用同一份真实 S07 数据走通以下检查：

### 从零开始

- 能指出当前使用的 Published Revision、输入、环境和资源绑定；
- 能看懂 Preflight 的通过、阻断、延迟和需确认项；
- 能在修正后重新检查，并知道旧报告已经失效；
- SubmitRun 结果未知时不会重复创建 Task。

### 运行中定位

- 能同时看到烧杯分支和粉桶分支的活动 / 等待 / 关注状态；
- 能区分“等待共享机器人”和“设备动作失败”；
- 能打开 NodeJob 的 input、output、feedback、attempt 和命令证据；
- 能找到阻断 S07 投粉的具体依赖，而不是只看到一个红色节点；
- 每个控制动作都能看到提交、生效和完成的不同阶段。

### 未知结果处置

- 能看到 Command ID、boot、最后响应、物料 Site 和 Host 账本状态；
- `UNKNOWN` 和普通失败显示不同的下一步；
- 物理放料成功、账本失败时不会出现自动重试搬运按钮；
- 对账或人工取消后，能看到审计记录、资源状态和下游准入变化；
- 无法安全解决时，运行会保持明确的待核对 / 受控停止状态。

## 7. 第五步完成判定

第五步现在可以判定为完成，理由是：

- 三种核心调试意图都有完整主路径；
- 每条路径都连接到运行时模型的状态轴、依赖、证据和处置动作；
- S07 的并行、共享机器人、物料账本和 UNKNOWN 都有具体分支；
- 每个动作都有前置条件和完成条件，没有把“点击按钮”当成结果；
- 任务流已经足以作为下一步信息架构和交互层级的输入。

下一步进入第六步：根据这三条流收敛信息架构和 UI 需求，确定哪个视图承担主线、哪些事实进入节点详情、哪些动作必须保持上下文，以及哪些内容只能渐进展开。
