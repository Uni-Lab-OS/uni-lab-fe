# 调试场景第三步：真实场景验证结论 v0.1

> 本文完成“真实场景验证”阶段。它验证问题定义是否能解释真实 SZLab 运行，不提前决定首页、导航或具体组件。

## 1. 验证范围和证据

- `szlab_poly_studio/workflows/single_sample_atomic_attachment_flow.py`

- `docs/validation/parallel-runtime.md`

验证结论基于代码、工作流定义、测试契约和运行文档的静态交叉检查。它还没有替代真实设备上的 UI / E2E 演练；后者属于后续原型验收阶段。

## 2. 样本一：S07 固体投粉

S07 是最小但足以暴露调试问题的样本：两条逻辑并行分支分别搬运烧杯和粉桶，二者竞争同一个机器人，随后在 S07 完成投粉。

它验证了五条事实链必须同时存在：

```text
运行意图
  → 物料和 Site 依赖
  → 设备命令执行
  → 物理位置与 Host 账本
  → 下游准入和处置动作
```

其中 `transfer_material_atomic` 还必须拆成取料、放料和 Host 记账三个阶段。物理放料成功而账本失败时，不能自动重发搬运；机器人 `UNKNOWN` 时，也不能按普通失败重试。S07 已经足以证明“节点红了”不是调试所需的状态模型。

详细事实见 [S07 调试场景事实表](./s07-debug-scenario-fact-table-v0.1.md)。

## 3. 样本二：单样品原子流程

单样品流程把同一问题扩大到完整实验链路。代码和文档显示它包含：

| 维度 | 真实情况 | 对调试界面的影响 |
| --- | --- | --- |
| 物料输入 | 8 个独立 `material_source`，包括烧杯、样品瓶、粗粉、精粉、试剂瓶、两路溶剂和 Tip 盒 | 不能只显示节点参数；必须能追踪每个资源实例及其用途 |
| 设备执行 | 多个工作站、共享机器人，以及 S07 / S06 / S09 / S04 等设备动作 | 必须区分设备在线、动作可执行、正在执行和被共享资源阻塞 |
| 物料转运 | 14 次标准转运，另有一次原子取料-倒液-放料 | 物料状态是运行事实的一部分，不能隐藏在资源管理页 |
| 并行关系 | 粉体准备、溶剂操作、拍照和收尾等阶段存在逻辑并行；共享机器人仍按执行声明串行 | 必须同时表达依赖并行和物理资源互斥 |
| 消耗和结果 | 两路溶剂各 10 mL，S09 液体试剂 0.5 mL，并产生照片、检测和工艺结果 | 需要显示库存准入、消耗事实和节点输出，而不是只显示成功 / 失败 |
| 收尾阶段 | 物料回收、样品瓶关闭、成品瓶入库等动作仍然影响运行终态 | “主流程完成”不能提前等同于“运行已收敛” |

### 3.1 长流程没有推翻原问题，而是补充了三条要求

**第一，依赖关系不是单纯的 DAG 边。**

一个节点可能依赖物料实例、Site、设备能力、库存数量、共享执行器和前一节点的证据。页面需要让用户知道“这个节点为什么还不能开始”，而不是只让用户看见它位于哪条边的下游。

**第二，逻辑并行不等于物理同时执行。**

`parallel()` 表示依赖上可以并行；调度器和 Execution Claim 再按共享设备实际串行。用户需要同时看到“分支已具备执行资格”和“当前正在等待哪一个共享资源”。一个时间轴无法单独承担这两个含义。

**第三，运行终态包括证据和资源收敛。**

动作返回成功不代表库存、Site、照片、检测结果和清理动作都已收敛。长流程要求调试人员沿着输入、执行、输出和收尾继续追踪，而不是在主动作成功处结束观察。

## 4. 对原问题定义的验证结果

| 原问题假设 | 真实场景证据 | 验证结果 |
| --- | --- | --- |
| 调试入口应围绕一次运行目标，而不是围绕对象分类 | S07 和单样品流程都从“定义版本 + 输入 + 资源 + 环境”开始 | **成立**。运行目标是最小认知单位 |
| 运行前需要一份可解释的准入结论 | 物料 Site、库存、设备能力、互斥和输入约束共同决定是否可执行 | **成立**。单一“在线”状态不够 |
| 定义层和运行层必须分开 | 工作流定义固定；每次 NodeJob、命令和物料账本是运行实例 | **成立**。编辑定义不能替代观察运行 |
| 并行需要结构、资源和时间三种事实 | `parallel()` 与共享机器人 Claim 同时存在 | **成立**。三者不能由单一视图互相替代 |
| UNKNOWN 需要独立处置路径 | 驱动重启会产生 UNKNOWN，且会阻断新的机器人运动 | **成立**。不能并入普通失败 |
| 资源详情应围绕当前调试决策收敛 | 长流程的资源实例、库存、Site 和消耗会随运行变化 | **成立**。资源事实必须回到运行上下文 |
| 输入输出和反馈是节点调试的核心证据 | S07 目标质量 / 天平读数，长流程照片 / 检测 / 密度等均为节点产出 | **成立**。必须支持按 NodeJob 查看 input、output、feedback |

## 5. 本阶段新增的产品事实

真实样本没有产生新的根问题，但把问题边界从“执行中状态混乱”精确到了以下五类运行事实：

1. **意图**：当前验证的定义修订、运行输入和仿真 / 真机环境。
2. **依赖**：资源实例、物料位置、库存数量、设备能力、共享资源和下游准入条件。
3. **执行**：NodeJob、动作阶段、命令 ID、设备见证和调度等待。
4. **账本**：物理位置、Host 物料记录、库存扣减和消耗结果。
5. **证据与处置**：输入输出反馈、历史记录、异常原因，以及当前允许等待、重试、对账、人工取消、继续或停止中的哪一种动作。

这五类事实是后续运行模型和 UI 需求的输入。它们不是五个一级导航，也不意味着页面必须分成五块。

## 6. 三个业务决策项的状态

| 问题 | 已从代码 / 文档确认的事实 | 仍需业务确认 |
| --- | --- | --- |
| 物理放料成功但 Host 记账失败，谁负责处理？ | 系统禁止自动重发；机器人支持 `reconcile`，也支持带理由的人工取消；错误处理文档要求操作员确认和人工处理 | 调试人员是否拥有发起对账的权限；现场核验由哪个角色完成；何时可以解除运行阻断 |
| S07 投粉的最终事实以什么为准？ | 动作返回包含命令目标、消息和可用的最终称量证据；历史写入失败时仍保留工艺结果并单独标记证据错误 | 产品上的“完成”是否要求 PLC / 天平读数、动作返回和历史记录全部满足；证据缺失是否允许继续 |
| 仿真是否覆盖异常路径？ | 仿真和真机复用设备动作签名；运行文档覆盖共享资源和并行调度；驱动测试覆盖 UNKNOWN 等故障状态 | 仿真默认是否注入 UNKNOWN、账本失败、Site 见证失败和资源互斥等待；哪些故障必须能在 UI 验收环境中稳定复现 |

这三个问题不阻塞问题定义，但会阻塞“处置动作权限”和“调试验收数据”的最终设计。

## 7. 第三步完成判定

第三步现在可以判定为完成，理由是：

- 已用一个最小真实样本验证单次运行的完整事实链；
- 已用一个长真实流程验证多物料、多次转运、并行、共享设备和收尾阶段；
- 已将原先的体验抱怨转成可观察、可验证的运行事实；
- 已识别出产品设计必须保留的三项业务决策，而没有用 UI 假设替代它们。

当前仍未完成的是运行时模型和界面结构设计。下一步应先定义这些事实之间的状态、依赖、证据和处置关系，再决定主视图、详情视图和入口组织。
