# Uni-Lab 任务调试产品设计 v0.1

> 状态：Draft · 产品结构与交互边界已确认，运行时合同待冻结
>
> 本文是任务调试产品设计的决策入口，记录已经达成的产品和领域边界。详细的问题定义、真实场景和任务流继续放在关联文档中，本文不复制它们的完整内容。

## 1. 产品目标

任务调试用于验证一个已发布工作流修订在指定输入、资源和运行环境下的实际执行情况，并帮助用户判断下一步动作。

用户在任何时刻都应该能够回答四个问题：

1. 当前验证的是哪个工作流版本和哪一次 Task？
2. Task 当前执行到哪里，整体进度如何？
3. 为什么某个节点正在运行、等待、阻塞或需要人工处理？
4. 当前允许执行什么动作，动作何时才算真正生效？

## 2. 产品结构

任务调试分成两个互补的层级：

### 2.1 任务监控入口

任务监控负责找回和筛选 Task：

- 复用现有 Task 列表作为多 Task 监控入口；
- 运行中、等待、异常、已完成筛选；
- 任务总体进度和最近更新时间；
- 当前关注节点、等待资源和结果未知摘要；
- 需要处理的 Task 快速入口；
- 进入某个 Task 的调试详情。

它回答的是：**我现在应该处理哪个 Task？哪些 Task 正在受到资源或异常影响？**

多 Task 监控不把多个 Task 的节点合并成一条时间线。每条 Task 保留自己的身份、进度、状态和控制入口；用户点击某一条后进入单 Task 调试详情。只有在未来出现共同创建、共同完成或整体控制的业务语义时，才增加 `TaskGroup` / `RunSet`，不能仅因为多个 Task 同时运行就新增一个批次对象。

### 2.2 单 Task 调试详情

单 Task 详情以执行时间线为主视图：

- 时间线展示实际发生顺序、分支、节点状态和当前关注点；
- 一个 Task 内的 `fork / branch / join` 作为时间线中的可展开执行块；
- 点击节点打开详情抽屉；
- 完整 DAG 作为按需结构视图；
- 资源、异常、输入输出和观测信息围绕当前节点展开。

它回答的是：**这个 Task 现在发生了什么，下一步怎么处理？**

第一屏不常驻展示完整资源面板、完整库位图或完整日志。

### 2.3 一个 Task 内的分支执行

单 Task 内的并行分支和多 Task 监控是两个不同概念：

| 场景 | 运行对象 | 用户选择的对象 | 页面形态 |
| --- | --- | --- | --- |
| 分支执行 | 一个 Task 内的多个 branch | 选择当前调试要先释放的节点 | 时间线中的并行执行块 |
| 多 Task 监控 | 多个独立 Task | 选择要进入详情的 Task | Task 列表的运行监控视图 |

分支节点还要区分两种语义：

1. **业务分支选择**：例如“是 / 否”，选择结果后只有一条分支可达；这是工作流业务语义。
2. **调试调度选择**：多个分支都已满足执行条件，用户选择先释放哪一个；这只改变本次调试的观察顺序，不修改 DAG，也不会跳过其他分支。

到达并行 `fork` 后，单步任务进入“选择下一步”状态。界面展示 OS 返回的 `ready frontier`，每个候选节点标明分支、资源、准入状态和等待原因。用户选择一个可执行节点后，提交带目标节点身份的 `step` 命令；其他分支保持 `ready` 或 `waiting`，直到各自被调度或被 OS 标记为不可达。

自动运行时不显示用户选择面板，由 OS 调度器按照运行策略决定分支顺序。分支汇合后的 `join` 必须展示未满足的准入条件，不能只显示一条汇合线。

## 3. 单 Task 第一屏

第一屏只保留调试主线：

1. Task 身份：工作流、Revision、Task、环境和 Edge 连接状态；
2. 运行控制：根据 OS 返回的状态显示允许的控制命令；
3. 整体进度；
4. 执行时间线；
5. 当前关注摘要：当前阻断点、影响范围和资源数量。

资源详情、异常详情、Trace 和日志通过节点详情抽屉访问。

## 4. 节点详情抽屉

节点详情包含以下视图：

| 视图 | 内容 |
| --- | --- |
| 概览 | 状态、时间、设备、分支、运行参数和运行结果 |
| 输入输出 | 实际输入、输出、反馈和执行尝试 |
| 资源占用 | 设备、试剂、物料、库位、持有者和冲突关系 |
| 异常阻塞 | 等待原因、异常、人工确认、可用处置动作 |
| Trace / 事件 / 日志 | Trace ID、运行事件、反馈事件和设备日志 |

节点详情展示的是 OS / backend 返回的运行事实，不由前端推测成功、失败或资源占用。

## 5. 资源和库位图

资源按当前节点的调试决策展示：

- 设备：在线、运行中、被占用、等待释放；
- 试剂：容器、余量、预留和消耗状态；
- 物料：实例、当前位置、锁定和转运状态；
- 库位：可用、占用、待选择、冲突和实际核验状态。

库位图采用按需展开，不作为第一屏常驻区域。

只有满足以下条件时才显示“查看库位图”：

- 当前节点涉及 Site / 库位；
- 用户需要选择目标库位；
- 存在位置冲突；
- 物理转运结算需要核对实际位置。

库位图只负责空间关系判断和库位选择，不承担设备三维监控。图上的暂选结果必须和异常阻塞中的确认控件共用同一个选择状态，不能形成两套提交逻辑。

## 6. 任务控制领域语义

### 6.1 普通任务

```text
normal + active
  ├─ pause  → normal + paused
  ├─ cancel → canceling → canceled / timeout
  └─ 进入单步 → switching_to_step → step + paused
```

暂停只关闭后续派发，在途设备动作自然结束；它不是急停，也不自动释放资源。

### 6.2 单步任务

```text
step + paused
  ├─ step(target_node_uuid) → 释放一个候选节点的调度边界
  ├─ resume                → normal + active
  └─ cancel                → canceling → canceled / timeout
```

单步不是“直接运行一个节点”，而是在 OS 返回的候选节点集合（`ready frontier`）中释放一次调度机会。串行流程通常只有一个候选节点；到达并行分支时，用户必须先从多个候选节点中选择一个。命令接受不代表节点已经完成，最终状态必须由 Task、NodeJob 和 feedback 投影确认。

当多个分支都可执行时，第一版只允许一次选择一个节点。选择一个节点只表达调试顺序，不能改变 Canonical revision、删除兄弟分支或把未选择分支标记为跳过。若候选节点因 Claim、Site、物料或设备能力不能执行，仍可展示，但必须明确写出阻塞原因并禁用选择。

### 6.3 “切换单步”的边界

推荐调试任务在创建时就使用 `run_mode=step`，从开始就进入调试暂停态，不需要把普通任务转换成调试任务。

如果未来必须支持普通任务运行中进入单步，应将它建模为 Debugger 专用能力或 Debugger Session 的动作，而不是让普通 Runtime 命令无限扩展。

共享 Task 命令只保留稳定的用户意图：

```text
step / pause / resume / cancel
```

前端不得根据按钮点击乐观修改 Task 的 `status`、`control_status` 或执行模式。

### 6.4 并行分支的控制边界

单 Task 内的分支控制遵循以下规则：

- `pause / resume / cancel` 作用于整个 Task；
- `step` 作用于用户选中的候选节点；
- 第一版不提供“取消单个分支”或“跳过单个分支”，除非 OS 已定义补偿、物料账本和 Join 语义；
- 自动运行时，分支调度顺序由 OS 决定，前端只展示结果；
- Join 节点只有在所有必要分支和资源、物料、证据条件满足后才进入可执行状态。

分支视图需要同时展示：分支状态、当前节点、`blocked_by`、等待原因、共享 Claim、分支进度和 Join 未满足条件。不能只用一条时间线或一个 Task 总状态替代这些事实。

### 6.5 多 Task 监控边界

多 Task 监控复用现有任务列表，不创建第二套调试页面。运行中的列表行至少展示：Task 身份、工作流 Revision、进度、生命周期、控制状态、当前关注点、资源等待 / 结果未知摘要和最近更新时间。

多 Task 页面只负责观察、筛选和进入某个 Task；暂停、继续、取消仍然是单 Task 命令。第一版不提供“暂停全部”“取消全部”或跨 Task 的单步操作，也不把多个 Task 的节点拼成一张共享时间线。

如果未来需要多个 Task 共同创建、共同完成或整体控制，再引入 `TaskGroup` / `RunSet` 作为独立领域对象，并定义它与成员 Task 的生命周期关系。多个 Task 同时运行本身不足以创建该对象。

## 7. 状态和颜色

状态必须同时通过文字、图标和样式表达：

- 绿色：节点成功；
- 橙色：节点运行中；
- 黄色：资源或依赖等待；
- 蓝色：暂停在节点之前；
- 紫色：用户选择或起始点；
- 红色：失败、异常或人工处置；
- 灰色：尚未到达或已跳过。

选中节点不能代替运行状态，蓝色选中态不能表示“正在运行”。

## 8. 当前 demo 与真实产品的边界

当前 demo 用于验证产品结构和交互路径，已经覆盖：

- 时间线主视图；
- 进度和当前关注；
- 节点详情抽屉；
- 输入输出、异常阻塞、资源占用和观测信息；
- 按需库位图及其选择联动；
- 单 Task 内并行执行块、候选节点选择、命令提交反馈和 Join 准入条件；
- 单步、继续和取消的视觉路径。

接入真实运行时后必须改为读取 `WorkflowRuntimePort` 的权威事实：

- `WorkflowTask`；
- `WorkflowNodeJob`；
- `WorkflowTaskStepState`；
- `WorkflowNodeJobFeedback`；
- 全局 workflow runtime SSE invalidation。

## 9. 已确认的产品决策和后续问题

### 9.1 已确认

1. 推荐创建 Task 时直接指定 `run_mode=step`；普通任务运行中进入单步不是当前共享 Runtime 的基础能力。
2. 人工确认、异常干预和库位选择保留不同的领域事实与处置流程，但可以在节点详情中使用一致的“待用户处理”布局语言。
3. `execution_unknown`、物理转运结算和执行锁释放属于安全恢复流程，不扩展普通的 `step / pause / resume / cancel` 命令。
4. 多 Task 监控复用现有 Task 列表，增加运行态摘要和实时筛选；当前不做多 Task 矩阵，也不把多个 Task 合并成一条时间线。
5. 单 Task 分支调试时，用户选择的是 `ready frontier` 中的下一个调度节点；不修改 DAG，也不隐式跳过其他分支。

### 9.2 后续需要和运行时合同一起确认

1. `step` 请求中目标节点、幂等键和 expected revision 的具体字段名称；
2. OS 如何返回 `ready frontier`、分支状态、Join 准入和候选节点不可选原因；
3. 多 Task 列表的进度计算依据和跨 Task 资源冲突投影；
4. 哪些业务场景需要 `TaskGroup / RunSet`，以及其整体控制和终态语义；
5. 人工确认、intervention、reconciliation 和执行锁恢复端口的冻结时间。

## 11. 人工确认、异常处理和状态完整性

截图中的三项不是三个可以直接加到页面上的状态标签，而是三类不同的运行事实。

### 11.1 人工确认

人工确认发生在节点已经获得调度资格、但设备动作尚未正式派发之前。它至少需要：

- 关联的 Task、NodeJob 和 attempt；
- 待确认的动作和上下文；
- `pending / approved / rejected / timed_out / canceled` 状态；
- 截止时间和允许动作（批准 / 拒绝）；
- 决定人、决定时间、理由和幂等身份。

OS 和旧版任务页已经有 `manual_confirmation` 事实和批准 / 拒绝接口。当前 `packages/services` 的新 `WorkflowNodeJob` 合同还没有把这组事实和命令端口完整暴露出来，因此需要扩展服务适配层，而不是新增一个前端自有的确认状态机。

运行前 Preflight 的 `confirmation_required` 或资源选择中的 `requires_confirmation` 属于提交前确认，不能和运行中的人工确认复用同一个对象。

### 11.2 异常处理

异常处理发生在动作失败、结果不确定或设备反馈要求人工决策之后。它和人工确认不是同一种事实，建议建模为独立的 `WorkflowIntervention`：

- `uuid`、`revision`、Task / NodeJob 身份；
- 动作名称、异常类型、错误消息和上下文；
- 后端返回的合法选项，例如 `retry`、`skip`、`abort`；
- 打开时间、截止时间和超时默认策略；
- 决策状态、决策人、理由和审计信息。

`waiting_intervention` 和 `intervention_required` 已经存在于 OS 的控制和 Job 状态中，但新 v1 服务端口还没有统一的 intervention 读取和决策接口。建议新增独立的 intervention read / command port，不把 `retry`、`skip`、`abort` 硬塞进通用 `WorkflowTaskCommandType`。

### 11.3 状态完整性

当前领域模型已经覆盖大多数截图状态：

| 截图状态 | 权威来源 | 处理方式 |
| --- | --- | --- |
| 失败 | Task / NodeJob `failed` | 保留原始失败事实和错误信息 |
| 取消中 | Task `canceling`、Job `cancel_requested` | 展示过渡态，不提前显示已取消 |
| 已取消 | Task / NodeJob `canceled` | 结合 cleanup 状态判断是否已经收敛 |
| 已跳过 | NodeJob `skipped` | 节点状态，不提升为 Task 终态 |
| 结果待核对 | `execution_unknown`、人工处理未完成或结果复核未完成 | 作为关注投影，不新增一个假的生命周期状态 |
| 结果未知 | NodeJob `execution_unknown` + `uncertainty_reason` | 必须进入核对路径，禁止盲目重试 |

因此不建议再增加一个笼统的 `attention` 或 `needs_review` 领域状态。页面可以生成“需要处理”的排序投影，但必须保留触发它的原始状态、原因码和来源身份。

### 11.4 需要补齐的 v1 服务合同

领域模型不需要新增三个平行实体，但新前端服务边界需要补齐：

1. `WorkflowNodeJob.manual_confirmation` 读模型及批准 / 拒绝命令；
2. `WorkflowIntervention` 列表、详情和带 revision / 幂等键的决策命令；
3. 结果未知后的 review / reconciliation 读模型和处置命令；
4. 节点结果复核信息，例如 review version、operator、时间和理由；
5. 统一的 Task / NodeJob 状态投影，避免旧 OS 前端和新 `WorkflowRuntimePort` 各自维护一套状态映射。

这些扩展应落在 OS/backend adapter 和 `WorkflowRuntimePort`，不应由 React 组件自己拼接状态或发私有请求。

## 12. 执行锁

执行锁不是普通的“资源占用标签”，而是调度安全事实。它保证同一设备、物料或库位不会被多个作业同时推进，并在设备、Host 或进程异常后保留足够的身份信息进行安全恢复。

### 12.1 锁的领域事实

一个执行锁至少关联：

- Task、NodeJob 和 attempt；
- 规范化的 `lock_key` 和语义范围（设备、物料、物料库位或其他资源）；
- Claim 身份；
- fencing token；
- 租约状态；
- Job / Task 当前状态；
- 物理设备托管状态；
- 是否允许人工处置及阻止原因。

锁不能被压成 `locked / unlocked` 两态。至少要区分：

```text
reserved → running → released
                    ↘ uncertain
```

`uncertain` 表示动作或物理结果可能已经发生，不能直接释放或重试。

### 12.2 交互分成四种路径

#### A. 正常等待

节点等待共享设备、物料或库位时，锁面板只读展示：

- 当前等待的资源；
- 当前持有者的 Task / Job；
- 等待开始时间；
- 阻断原因和影响的下游节点。

此时不显示“强制解锁”。用户应该进入持有者 Task 或等待调度，不直接修改锁事实。

#### B. 正常持有

节点正在执行时，锁只作为资源上下文展示：

- 谁持有；
- 当前 Job 状态；
- 设备、物料或库位的语义名称；
- 预计由哪个终态事件释放。

释放动作不能因为用户打开了资源详情就出现。

#### C. 异常终态后残留

当 Task 已经 `failed / canceled / timeout`，但仍有活动执行锁时，显示“需要处理”而不是普通等待：

1. 先展示后端返回的释放资格和阻止原因；
2. 按 Job / Claim 分组，而不是让用户逐个锁操作；
3. 展示本组锁的 scope、lock key、Claim、Fence 和 Job 状态；
4. 只有后端确认 `can_release=true` 时才显示人工释放入口。

后端的人工释放会释放该 Job 的整组活动锁，因此 UI 不应伪装成单个锁的独立开关。连续区间锁还必须使用任务级整组释放。

#### D. 结果不确定或物理转运未结算

锁或 Claim 处于 `uncertain`，或者物料转运的物理位置与 Host 账本尚未对齐时，不能直接解锁。

交互顺序应是：

```text
查看未知结果
  → 读取物理结算上下文
  → 现场选择真实库位 / 物理事实
  → 填写结算原因并确认
  → OS 更新账本并释放相关锁
```

“完成物理结算”和“人工解除执行锁”是两个不同动作，不能合并成一个通用确认框。

### 12.3 人工释放的安全门禁

人工释放必须由 OS 重新判断，前端不能自行计算资格。至少包括：

- Task 是异常终态；
- Job 是终态；
- 没有活动设备托管；
- 没有未解决的结果不确定原因；
- Claim 仍然属于该租约；
- Fence 与页面读取时一致；
- 用户填写人工释放原因；
- 用户确认设备已停止且物理现场安全。

提交时必须带上 `expected_claim_uuid` 和 `expected_fencing_token`。如果 Claim 或 Fence 已变化，后端应拒绝本次操作，UI 关闭确认状态、重新读取锁快照并提示用户重新判断。

提交成功后不能乐观地从页面删除锁。页面应依次显示：

```text
操作已接受 → 重新读取锁快照 → 锁已释放 / 仍需处理
```

每次人工释放都要保留原因、操作人、时间、目标 Job、Claim、Fence 和释放的锁列表，供运行事件和审计查询。

### 12.4 领域模型是否完备

OS 的执行锁领域已经具备核心事实：Lease、Claim、Fence、scope、`reserved / running / uncertain`、Job / Task 关联、设备托管、释放资格、CAS 校验和操作审计。核心模型不需要再增加一个“锁状态总对象”。

当前缺口在新的前端服务边界：

1. `WorkflowRuntimePort` 尚未暴露任务执行锁快照；
2. 新 v1 合同没有统一的 Lock / Claim / Fence 类型；
3. 人工释放、物理结算和结果核对的安全操作还没有归入统一的 OS-only recovery port；
4. UI 需要同时读取锁事实、物料事实、Job 状态和设备托管状态，不能只读取一个 `locked` 字段。

因此，执行锁恢复应作为独立的安全恢复接口接入，不应扩展普通的 `step / pause / resume / cancel` Task 命令，也不应由 React 组件直接调用旧的私有接口。

## 13. 产品验收标准

产品验收按用户任务和权威运行事实判断，不按页面是否出现某个按钮判断：

| 场景 | 用户必须能够完成的判断或操作 | 验收依据 |
| --- | --- | --- |
| 找回 Task | 从任务列表识别工作流、Revision、Task 状态、进度和当前关注点，并进入详情 | Task 列表读取同一份运行态投影 |
| 查看执行主线 | 在第一屏看懂当前节点、已完成节点、等待 / 阻塞原因和整体进度 | Task、NodeJob 和全局事件重新读取后的状态 |
| 串行单步 | 选择可执行节点并提交一次单步，区分命令已接受和节点已生效 | command accepted、Task / NodeJob 状态、feedback |
| 并行分支 | 看到 `ready frontier`，理解各分支的准入条件，选择一个候选节点执行 | OS 返回的候选节点、分支状态和 Join 条件 |
| 人工处理 | 区分人工确认、异常干预、结果核对和库位选择，并完成合法处置 | 对应的确认 / intervention / reconciliation 事实及审计记录 |
| 资源与库位 | 查看当前节点的资源占用；需要空间判断时打开库位图并提交同一份选择 | Resource、Material、Site 和锁快照 |
| 异常恢复 | 遇到 `execution_unknown`、残留锁或物理转运未结算时，按安全门禁进入恢复流程 | OS 返回的资格、Claim、Fence 和恢复结果 |
| 多 Task 监控 | 在同一任务列表观察多个 Task，但进入某一条后仍只控制该 Task | 每条 Task 独立的身份、状态和控制命令 |

所有命令都必须满足以下共同验收条件：

1. 提交后显示 durable accepted 与实际生效状态的区别；
2. 页面不通过计时器或乐观更新伪造节点、Task、锁或资源状态；
3. 断线重连后能通过 SSE invalidation 和 REST 投影恢复到同一状态；
4. 错误、等待、结果未知和取消中都保留可行动的原因与来源；
5. 关键状态同时有文字、图标和可访问标签，不能只靠颜色区分。
