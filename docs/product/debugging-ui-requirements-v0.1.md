## 1. 先确定产品主线

Uni-Lab 第一阶段的核心用户是负责设备、工作流和实验运行联调的调试人员。他们打开系统不是为了浏览所有资源，而是为了完成一次可解释的调试运行：

```text
选择工作流版本
  → 填写本次运行输入
  → 选择或确认设备、物料、试剂和库位
  → 运行 Preflight
  → 在仿真或真机环境启动调试
  → 观察节点执行和并行关系
  → 查看节点 input / output / 反馈 / 证据
  → 暂停、单步、继续、取消或处理异常
  → 得到可追溯的运行结果
```

页面的主问题应始终是：

1. 这次运行是什么，使用哪个工作流版本和环境？
2. 现在卡在哪里，为什么卡住？
3. 我下一步能做什么？
4. 这个结论由什么输入、输出或设备证据支持？

“设备、物料、试剂、实验室操作、工作流、任务”是领域对象或场景能力，不应自动变成六个同等重要的一级页面。

## 2. 信息架构收敛

第六步之后，不再把“工作台、工作流、运行、资源”理解成四个平级产品分类。当前信息架构以一个调试主线工作区为中心：

```text
调试工作台（默认入口）
  ├─ 开始新的调试：已发布修订 → Run Preparation → Preflight → SubmitRun
  ├─ 继续处理运行：关注事项 → 当前运行路径 → NodeJob / Evidence → 处置
  └─ 最近上下文：最近运行、定义和资源

支撑空间
  ├─ 定义与版本：工作流、实验室操作、设备动作的浏览与高级编辑
  └─ 资源与现场：设备、物料、试剂的事实、历史与维护
```

运行详情是调试主线的核心工作区；定义与资源只提供支撑事实，不与当前运行争夺首屏注意力。完整的职责、进入规则和上下文保持规则见 [调试信息架构与交互层级](./debugging-information-architecture-v0.1.md)。

领域层级仍然保留：

```text
设备动作 → 实验操作（可复用子工作流） → 工作流 → 一次运行 / Task
```

它们以定义层、运行层和资源层的不同职责呈现，不再分别制作相互竞争的“调试首页”。实验室操作编辑器、源码编辑器、AI 创建设备、生产排程和发布审核均属于高级或后续场景，不进入调试主线首屏。

调试模式中的环境统一叫 **仿真 / 真机**；它与自动运行、单步控制和 Task 生命周期分开建模。

## 3. 核心页面需求

### 3.1 调试首页

首页只承担恢复上下文和开始任务，不做全量监控大屏。

首屏区域：

- **当前环境**：仿真或真机、连接状态、最后同步时间。
- **待处理事项**：结果待核对、等待资源、执行未知、需要人工确认；按紧急程度排序。
- **活动运行**：显示运行名称、工作流版本、整体关注状态、活动节点数、最近更新时间。
- **最近工作流**：显示版本、校验状态、最近一次运行结果。
- **主要动作**：`选择工作流开始调试`；次要动作 `调试设备动作`。

不在首页展示资源总数、生产排程、复杂统计图或所有历史事件。

### 3.2 工作流目录与详情

工作流列表每行只显示调试决策所需的信息：

- 名称和业务说明；
- 当前可用修订；
- 校验 / 发布状态；
- 输入数量和资源需求摘要；
- 最近一次运行结果；
- `开始调试`。

工作流详情分成三块：

1. **流程预览**：只读 DAG，显示分支、合并、循环和实验操作边界。
2. **运行需求**：输入参数、设备能力、物料 / 试剂 / 库位需求；使用人类可读名称。
3. **版本上下文**：明确本次使用的 Published Revision，不随 Draft 后续修改而变化。

调试页面不要求用户先理解 Canonical JSON、内部 UUID 或执行计划。技术标识只在详情或复制入口出现。

### 3.3 运行准备（Run Preparation）

从工作流点击 `开始调试` 后进入单页准备流程，页面按顺序呈现：

```text
工作流与修订 → 运行输入 → 资源选择 → Preflight → 开始调试
```

要求：

- 只显示当前工作流真正需要的输入；
- 参数错误在字段附近说明，不能等到提交才统一报错；
- 设备、物料、试剂和库位选择显示候选状态、位置、可用量、占用和新鲜度；
- 用户选择的是本次运行的候选绑定草稿，不直接修改物料、库存或设备状态；
- Preflight 按检查组展示 `通过 / 警告 / 阻断 / 过期 / 无法判断`；
- 点击一条阻断项可直接打开对应资源或字段；
- `开始调试` 只有在阻断项清除后可用；提交时仍由 OS / Backend 再次校验。

Preflight 检查组固定为：工作流定义、输入、设备与动作、物料与库位、试剂与库存、冲突与占用、连接与数据新鲜度。当前 OS 的 Preflight 是唯一准入判断，前端可以做字段完整性提示，但不能根据分散读取的设备、物料或库存自行宣布“可运行”。

### 3.4 运行详情（Task Runtime）

运行详情是调试场景的核心页面，首屏采用“当前关注 + 当前运行路径 + 详情”的三栏关系；完整结构图按需展开：

```text
┌ 运行头部与控制 ─────────────────────────────────────┐
│ 关注提示 / 阻断原因                                 │
├───────────────┬──────────────────────┬─────────────┤
│ 当前运行路径    │ 活动 / 等待 / 关注列表 │ 节点详情抽屉 │
│ 阻断链、分支    │ 可点击定位节点         │ input/output │
│ 上游依赖        │ 共享资源等待           │ 反馈、证据   │
├─────────────────────────────────────────────────────┤
│ 事件与执行证据（按需展开）                           │
└─────────────────────────────────────────────────────┘
```

运行头部应显示（字段是否可见以 OS 返回为准）：

- 运行名称、工作流名称、Revision、环境（仿真 / 真机）；
- 总体关注状态；
- 逻辑生命周期、控制意图、清理状态，以及 OS 已提供的物理关注 / 结算信息；
- 当前可执行控制：`暂停`、`单步`、`继续`、`取消`，只显示 OS 返回的可用操作；
- 连接中断、状态过期、命令已提交但尚未生效等事实。

节点详情按 `executor_kind` 变化，不强行使用一套字段：

- 设备动作：动作参数、目标设备、命令、尝试次数、设备反馈、物理证据；
- 物料转移：来源物料 / 库位、目标库位、数量、占用和结算；
- 试剂来源：试剂目录、具体库存容器、批次、余量和绑定原因；
- 条件 / 循环：条件输入、判断结果、分支路径、迭代次数和子节点；
- 计算 / 脚本：输入、输出、日志和诊断；
- 人工确认：待确认内容、截止时间、确认结果和操作记录。

默认只展开当前选中的节点；完整 DAG、反馈、原始日志和证据放在可展开的下方面板或结构视图，避免详情页首屏被低频信息淹没。

### 3.5 运行列表

运行列表用于找回和比较运行，不承担运行详情的全部内容。默认排序为“需要处理 → 运行中 → 最近结束”。每行显示：

- 运行名称、工作流版本、环境；
- 总体关注状态；
- 活动 / 等待 / 需要处理的节点数；
- 最近更新时间；
- 打开运行详情。

运行列表使用普通列表或分组列表；并行关系在运行详情的 DAG 和活动集合中表达。Timeline 只作为事件顺序视图，不能作为唯一的运行模型。

### 3.6 设备动作调试

设备动作调试是低级调试入口，和工作流调试共用运行详情的状态和证据组件：

```text
选择设备 → 选择动作 → 填写参数 → 执行前检查 → 仿真 / 真机执行 → 查看结果
```

设备页只显示设备身份、在线 / 离线 / 未知、当前动作能力、实时状态摘要和最近动作结果。设备由环境或设备包提供，当前不提供常规增删改查。设备配置、源码和设备包导入属于高级维护入口，默认折叠。

## 4. 领域对象在 UI 中的边界

| 对象 | UI 主要关注点 | 不应承担的职责 |
| --- | --- | --- |
| 物料 Material | 当前状态、当前库位、占用 / 预留、关联运行、容器和标签；列表名称使用“显示名 + 类型 + 条码 / 批次” | 首屏展示完整几何、所有历史字段或内部结构 |
| 设备 Device | 在线状态、动作能力、当前调试状态、最近反馈 | 在调试页增删设备、维护生产排程 |
| 试剂目录 Reagent Catalog | CAS 号对应的化学身份、基础理化信息、版本 / 变更历史 | 直接表示某个库存容器的余量 |
| 试剂库存 Reagent Inventory | 具体容器、供应商 / 批次、浓度、物性、余量、单位、库位、状态 | 复制一份化学主数据 |
| 工作流 Workflow | 已发布修订、输入契约、资源需求、DAG、最近运行 | 在运行中修改本次执行定义 |
| 实验室操作 | 可复用的子工作流 / 节点；在图和节点详情中显示 | 作为独立的第三套执行模型 |
| 运行 / Task | 一次具体的工作流执行、控制、关注事项和证据 | 把所有执行事实压成一个 status |
| 节点作业 NodeJob | 本次运行中一个节点的实例、input / output、状态和可用操作 | 只用 workflowNodeUuid 表示循环中的多个实例 |

试剂 UI 必须明确分离两个关注点：

```text
试剂目录：按 CAS 号识别同一种化学物质，查看身份和变更历史。
试剂库存：按具体容器 / 物料记录库存变体，允许同一 CAS 存在多供应商、浓度、物性和容器。
```

只有带 `container` 标签的物料才可作为试剂容器。试剂库存详情应能跳转到绑定物料和库位，但不复制物料事实。

试剂库存需要完整的业务维护入口（新增、查询、编辑、移除 / 关闭）。界面上的“移除”应保留历史台账并明确说明影响范围，不做无痕硬删除；试剂目录同样支持新增、查询、编辑，目录详情提供独立的变更历史组件。当前 `packages/core` 的 `ReagentInventoryPort` 仍以查询为主，因此在调试工作台中先提供可靠的只读状态；维护按钮必须等对应的命令端口和后端合同明确后再接入。

## 5. 并行、分支和时间展示

运行调试不使用完整 DAG 或甘特图作为首屏主视图。甘特图适合生产排程，不适合回答“当前哪些节点同时在运行、哪个节点阻塞了下游”；完整 DAG 也不应要求用户自行从复杂布局中寻找阻断点。

运行详情的规则：

- 当前运行路径是主视图，表达当前关注节点、未完成上游依赖、下游阻断和共享资源等待；
- 完整 DAG 是按需打开的结构视图，表达依赖、分支、合并和循环；
- “当前节点”改为 **当前活动节点集合**，允许同时有多个运行、等待或关注节点；
- 每个动态循环实例使用 `jobUuid` 和迭代信息标识；
- 活动列表点击后高亮 DAG 节点并打开节点详情；
- Timeline / 事件面板按时间排序，显示并行事件的发生顺序，但不替代 DAG；
- 多个运行之间使用运行列表分开，不能把不同 Task 的节点拼成一张矩阵后要求用户自行推断。

## 6. 状态表达和交互规则

状态必须同时包含文字、图标或结构，颜色只作辅助：

- 绿色：已确认成功或在线；
- 橙色：运行中、等待注意或调试中；
- 蓝色：暂停在节点执行前；不能表示运行中；
- 紫色：本次运行起始点或物料身份；
- 红色：断点、异常或危险操作；
- 灰色：起点前、不可达或已跳过。

页面级规则：

1. 每个页面只有一个主要任务和一个主要按钮。
2. 资源详情、原始日志、版本差异和证据使用抽屉或下方面板渐进展开。
3. 关键入口不能只在 hover、右键或双击中出现；快捷方式可以保留，但必须有可见按钮。
4. 用户从运行进入资源详情后，返回仍保留运行、节点和筛选上下文。
5. 操作按钮旁边说明影响范围和阻断原因；命令“已提交”不能显示成“已完成”。
6. 页面不使用多个互相竞争的二级导航；同一对象只有一个事实来源和一个稳定 ID。

## 7. 版本范围

### P0：调试闭环

- 仿真 / 真机环境选择和连接状态；
- 工作流目录、已发布修订和只读 DAG 预览；
- 运行输入、资源候选和 Preflight；
- 创建调试运行；
- 运行详情：DAG、活动节点集合、并行、节点 input / output、反馈、异常和证据；
- 暂停、单步、继续、取消及命令生效状态；
- 活动和历史运行列表；
- 设备、物料、试剂的上下文状态抽屉；
- 试剂库存和试剂目录的基本分离展示；调试首屏支持库存查询和按 CAS 查询目录。

### P1：资源维护与低级调试

- 设备动作单点调试；
- 试剂库存命令端口明确后，接入库存新增、编辑、移除 / 关闭；
- 试剂目录新增 / 编辑和历史记录组件；
- 物料容器、标签和库位的状态维护；
- 运行证据导出和更细的反馈视图。

### 暂缓

- 设备常规增删；
- 拖拽式工作流创作和复杂节点库；
- 调试首屏的实验室操作独立工作台（定义层高级编辑入口保留）；
- 生产排程、甘特图、自动排程；
- 发布审核、双人签名和生产异常中心；
- AI 创建设备、源码 IDE 和全量版本对比；
- 面向所有资源的首页统计大屏。

## 8. 验收标准

以下路径能够在不离开主上下文的情况下完成，作为第一轮 UI 设计和 E2E 的验收基线：

1. 用户从工作流列表选择一个已发布修订，能看懂它需要哪些输入和资源，并开始调试。
2. 缺少物料、设备离线、库存不足或数据过期时，Preflight 能指出具体阻断对象和下一步入口。
3. 用户能明确看到本次运行处于仿真还是真机；真机动作有明确的风险和确认边界。
4. 两个或更多节点并行运行时，用户能在一次扫视中看到全部活动节点，并分别查看 input / output。
5. 节点失败、结果未知、等待人工确认和结算未完成不会被统一显示为“失败”。
6. 用户从节点详情跳到物料、试剂或设备后，能返回原运行和原节点。
7. 命令提交后，界面先显示“请求已提交 / 等待权威状态”，只有服务端确认后才显示最终结果。

## 9. 与当前前端领域实现对齐

当前 `packages/core` 已经提供了四个可组合的场景，而不是四套运行内核：

```text
Run Preparation
  PublishedWorkflowRevision → RunConfiguration / BindingDraft → Preflight → SubmitRun

Workflow Debugging
  TaskRuntimePresentation → TaskRuntimeDetail + Jobs → NodeJobDetail + Feedback

Device Action Debugging
  DeviceSummary + ActionDefinition → DeviceActionRun → 复用 Task / NodeJob 读取

Laboratory Operations
  TaskRuntimePresentation + DeviceSummary + Intervention
```

这对 UI 有四个直接约束：

1. **工作流调试和设备动作调试共用运行详情组件。** 设备单点动作创建的也是 Task / Job，不再设计一套设备专属运行状态页。
2. **运行列表先消费 OS 的 `TaskRuntimePresentation`。** 列表可使用 `status`、`runMode`、`controlStatus`、`cleanupStatus`、`attentionReason` 和内嵌 Job 摘要；进入详情后再读取 Task、Jobs、NodeJob 和 Feedback。
3. **前端不能自行拼装权威运行总状态。** 当前没有统一 `TaskRuntimeSummary` 端点，因此“物理关注”“结算”缺失时应显示未提供或隐藏，不能由 FE 根据 Job 状态推断。
4. **Run Preparation 中的候选不是新的领域实体。** 当前设备、物料、Site、Inventory 是分散查询，`BindingDraft` 只保存场景选择；候选列表应标注来源和观察时间，真正的可运行性以 OS POST Preflight 为准。

当前已实现的领域事实也应直接影响页面命名：

- Workflow 已明确区分 `workflow` 和 `experiment_operation` 两种已发布类型；后者在 UI 中可作为“实验操作 / 子流程”筛选或节点类型展示，并保留定义层的高级编辑入口，但不与调试主线平级竞争。
- Material 读模型包含 Material Graph、Site 和 Occupancy；物料列表应优先展示名称、类型、条码 / 批次、当前 Site、占用是否已知和关联运行。
- Device 读模型包含 `online`、`edgeStatus`、`dispatchable`、阻断原因、执行占用和动作状态；设备页应以这些事实为准，不把“有动作定义”当成“当前可执行”。
- NodeJob 详情已经能提供 `param`、`feedbackData`、`returnInfo`、`controlData`、`errorInfo`、`uncertaintyReason`、尝试次数和设备 / Edge 命令身份；节点详情可以围绕这些字段组织，而不需要额外发明“步骤实体”。
- Reagent 目录、具体试剂容器和通用 Inventory lot / instance 是不同读模型；UI 可以把它们编排成“目录 / 容器库存 / 数量批次”三层信息，但不能合并为一个万能库存对象。
- `RunPreparationStore` 是场景级草稿状态，Query Cache 只保存服务端读模型；输入、绑定选择、Preflight 结果和提交结果不能写进全局领域 Store。

因此，运行时模型中的状态轴应保留为产品观察框架，但在 UI 规格中标记为“服务端已提供才展示”，不能作为前端本地计算规则。

## 10. 两套参考界面的实际问题：不是功能太多，而是层级混在一起

这次补做了两套参考实现的交互审计，结论和之前的“收敛成四个入口、实验室操作不再独立”有一处重要修正：**能力本身不能简单砍掉，真正需要砍掉的是同一页面里的竞争性关注点。**

### 10.1 `uni-lab-os/frontend` 已经形成了四条不同的用户路径

- `WorkflowsPage` 同时承载工作流目录、已发布修订、DAG 拓扑、输入 / 输出合同、Preflight、物料绑定和创建任务；其中“拓扑 / 合同 / 诊断 / 运行准备”已经是四个不同的认知任务。
- `OperationsPage` 是真正的实验操作定义编辑器：设备 Action 和控制节点库、参数合同、子工作流引用、设备实例绑定、节点顺序调整、保存 / 发布 / 导入都在同一编辑面内。
- `TasksPage` 是并行运行矩阵，不只是任务列表。它同时提供活动节点、节点详情、input / output / feedback / error、暂停、单步、继续、取消、人工确认、干预和执行锁处置。
- `DevicesPage` 把设备实例、动作能力、运行时能力、参数校验、动作执行和最近 Job 结果串成一条低级调试路径；设备动作执行后仍回到 Task / Job 读取。
- `ReagentsPage` 已明确分成“库存”和“目录”，并实现容器标签筛选、CAS 目录、历史、录入、编辑、删除和分装；这不是一个简单的静态资源列表。

因此，OS 前端的问题不是没有主线，而是把“定义、准备、运行、处置、资源维护”压缩在少数几个超大页面中，导致页面内的二级任务彼此争夺注意力。

### 10.2 原型进一步证明了这种混杂

原型的导航明确包含“设备动作、实验操作调试、工作流调试、实验任务”，另有设备、试剂、物料公共资源中心。实际交互中：

- 实验操作页同时展示操作库、流程树、节点画布、运行输出和操作设计检查器；
- 工作流页同时展示工作流库、嵌套流程树、编辑画布、节点检查器和调试运行；点击运行后又在同一页面加入下一步、继续、暂停、受控停止、检查点恢复和补偿路径；
- 实验任务页同时承担任务列表、排程 / 进度、暂停、人工异常和任务详情；
- 设备动作页同时承担设备状态、动作目录、参数、前置条件、执行、反馈和 Trace。

这些页面把“我现在要做什么”与“这个对象的所有可能信息”放在了一起，所以用户会感觉凌乱。特别是工作流编辑和运行调试共用一张画布，容易让用户误以为运行中仍可修改定义；任务页的排程 / 处理 / 运行观察也没有明确区分。

### 10.3 修正后的信息架构

审计阶段曾经把“工作台、工作流、运行、资源”描述成四个一级入口。第六步之后，这个说法只保留为路由职责，不再把它们视为四个平级产品主线：

```text
调试工作台（默认入口）
  ├─ 开始新的调试：已发布修订 → Run Preparation → Preflight → SubmitRun
  ├─ 继续处理运行：关注事项 → 当前运行路径 → NodeJob / Evidence → 处置
  └─ 最近上下文：最近运行、定义和资源

支撑空间
  ├─ 定义与版本：工作流、实验室操作、设备动作的浏览与高级编辑
  └─ 资源与现场：设备、物料、试剂的事实、历史与维护
```

其中：

1. **调试工作台和运行工作区共同承担主线。** 工作台负责恢复或启动，运行工作区负责定位和处置。
2. **定义与版本按层级浏览，不与运行竞争。** 编辑器与运行观察使用不同路由 / 页面状态，不能共用同一主画布。
3. **运行详情首屏先显示当前关注和当前运行路径。** 完整 DAG、事件、Timeline 和原始日志按需展开。
4. **资源是上下文支撑空间。** 从运行进入资源时保留 Task、NodeJob 和筛选上下文；资源维护和运行时只读状态要视觉上分开。

### 10.4 对当前文档结论的具体更正

- 不再把“实验室操作独立模块”描述成应被删除的能力；应删除的是它在调试首屏的独立竞争位置。它仍是定义层中的可复用子工作流，并需要独立的高级编辑入口。
- 不再把“仿真 / 真机”只当成 `runMode` 的显示文案。它是运行上下文，必须与自动运行 / 单步控制分开建模和展示。
- 不再把任务页简化成普通列表。并行矩阵、活动节点集合、节点 input / output、人工处置和执行锁是调试闭环的一部分；需要做的是把低频处置折叠到运行详情的上下文面板。
- 不再因为当前 core 端口暂未齐全而删除产品需求。缺少命令端口、资源候选接口、证据导出接口，应该标记为实现缺口，并在 UI 合同中保留“权威状态 / 命令已提交 / 尚未生效”的状态。
- 物料、设备和试剂不应只做“状态抽屉”。OS 前端已证明它们存在维护、历史、绑定和现场处置路径；调试工作台只引用这些能力，不把它们全部塞进运行页面。

## 11. 仍需通过真实场景确认的问题

这份基线已经足够开始信息架构和线框设计，但以下问题需要用一条包含设备动作、物料转移和试剂消耗的真实 Workflow 验证：

- 单步调试的最小语义是暂停前节点、执行一个 NodeJob，还是执行到下一个断点；
- Preflight 是否返回统一的跨领域摘要，还是需要前端分别读取设备、物料和库存检查；
- 试剂“变更历史”是目录版本历史、库存台账，还是两者都需要；
- 物料当前状态的最小字段和实时刷新频率；
- 结果未知时需要哪些 Evidence / Intervention 操作才能继续、重试或结算；
- 实验操作是否始终作为已发布子工作流引用，还是仍需保留一类独立的操作定义编辑入口。

在这些语义确认前，不应继续增加新的一级模块或为每个后端对象制作独立的万能详情页。
