## 1. 先确定一条原则

调试产品的第一层不是“设备、物料、试剂、工作流、任务”分类，而是用户当前要完成的任务：

```text
开始一次验证
  或
继续处理一次运行
  或
查看支撑当前运行的定义 / 资源事实
```

因此，信息架构采用“一个主线工作区 + 两个支撑空间 + 上下文详情”的层级：

```text
调试工作台（默认入口）
├── 开始调试：Definition Revision → Run Preparation → Preflight → SubmitRun
├── 继续运行：Attention → Current Path → NodeJob / Evidence → Disposition
└── 最近上下文：最近运行、最近定义、最近访问资源

支撑空间
├── 定义与版本：工作流、实验室操作、设备动作的浏览 / 高级编辑
└── 资源与现场：设备、物料、试剂及其事实 / 维护

上下文详情
└── 运行、节点、设备、物料、试剂详情均以抽屉 / 侧面板进入，保留当前任务上下文
```

这意味着“工作台、运行、定义、资源”可以作为路由职责存在，但它们不是四个平级的产品主线。工作台和运行承担调试任务；定义与资源负责提供支撑事实。

## 2. 用户进入系统后的决策路径

首屏只做一件事：帮助用户选择“开始新的调试”还是“继续处理已有运行”。

```text
进入调试工作台
  ├─ 有需要处理的运行
  │    └─ 按安全核对 / 人工干预 / 准入阻断 / 运行中排序
  │         └─ 进入对应运行详情
  ├─ 没有需要处理的运行，但有活动运行
  │    └─ 继续运行
  └─ 开始新的调试
       └─ 选择已发布 Definition Revision
            └─ 进入 Run Preparation
```

工作台首屏可以显示最近运行和最近使用的定义，但它们的作用是恢复上下文，不是提供资源总览、统计大屏或全量监控。

首屏必须有两个主动作：

- **继续处理运行**：进入已有 Task，不创建新运行；
- **开始新的调试**：进入已发布修订选择，不直接进入空白画布。

设备单点调试作为“开始新的调试”的次级入口。它创建的仍然是标准 Task + 单个 NodeJob，随后进入同一套运行详情。

## 3. 信息架构的四层职责

### 3.1 调试工作台：恢复和启动

工作台只承担：

- 当前需要处理的运行；
- 当前环境是仿真还是真机，以及连接 / 数据新鲜度；
- 开始新的调试；
- 最近运行和最近使用的定义。

工作台不承担：

- 完整设备、物料、试剂管理；
- 工作流编辑；
- 所有任务的矩阵监控；
- 生产排程和统计大屏。

工作台上的“待处理”必须直接链接到运行详情中的具体事实，例如 `execution_unknown`、账本冲突、等待 Claim 或人工确认，而不是只有一个数量徽标。

### 3.2 运行工作区：调试主线

运行工作区是整个产品的核心。它回答：

1. 这次运行是什么？
2. 当前最需要处理的事实是什么？
3. 哪条分支、哪个节点或哪个资源造成了阻断？
4. 下一步允许做什么，完成条件是什么？

运行工作区采用四层信息层级：

```text
固定上下文栏
  → 当前关注栏
      → 当前执行路径 / 活动节点集合
          → 选中 NodeJob 的详情、证据和处置
```

完整工作流拓扑、事件 waterfall、资源详情和原始日志都从这条主线按需展开，不抢占首屏。

### 3.3 定义与版本：理解“要验证什么”

定义空间提供：

- 已发布 Workflow Revision 的目录和版本上下文；
- Workflow 的只读结构预览、输入合同和资源需求；
- 实验室操作作为可复用子工作流的浏览与高级编辑；
- 设备动作定义、参数合同和高级设备包维护。

默认顺序是：

```text
工作流修订 → 运行需求 → 子流程 / 动作边界 → 高级编辑
```

定义空间与运行空间必须使用不同路由 / 页面状态。运行中的 Definition Revision 只读，不能因为打开编辑器而改变当前 Task。

### 3.4 资源与现场：提供事实和维护

资源空间提供设备、物料和试剂的长期事实、历史和维护能力，但不承担调试主线。

资源空间的两种进入方式必须区分：

| 进入方式 | 用途 | 返回行为 |
| --- | --- | --- |
| 从运行 / Preflight / NodeJob 进入 | 查看该资源对当前运行的影响 | 返回原 Task、原 NodeJob、原筛选和滚动位置 |
| 从资源空间直接进入 | 搜索、维护、查看历史和现场状态 | 返回资源列表和筛选上下文 |

运行上下文中的资源详情默认显示当前状态、绑定关系、Site、占用、数量和影响；完整历史、目录变更和维护命令通过二级面板进入。

## 4. 运行工作区的主视图决策

### 4.1 主视图不是完整画布

S07 已经证明完整 DAG 不能单独回答“现在先处理什么”。因此运行详情的默认主视图不是缩小后的全量画布，而是 **当前运行路径**：

```text
当前关注点
  → 阻断节点 / 当前节点
      → 仍需满足的上游依赖
          → 允许的下一步动作
```

当前运行路径需要显示：

- 当前被关注的 NodeJob；
- 它所在的分支 / 子流程；
- 上游未完成依赖；
- 下游被阻断范围；
- 共享设备或 Claim 的占用关系；
- 当前动作和证据的最短摘要。

完整 DAG 作为“结构视图”按需打开，支持定位、缩放、分支过滤和回到当前路径；不要求用户在全量布局中自己寻找红色节点。

### 4.2 当前关注栏是首屏锚点

当前关注栏按以下优先级选择内容：

```text
安全核对 / 结算阻断
  > 人工干预
  > 准入 / 资源阻断
  > 活动执行 / 共享资源等待
  > 证据不完整
  > 已完成且已收敛
```

每个关注项必须有四个字段：

| 字段 | 作用 |
| --- | --- |
| 当前事实 | 发生了什么，如 `UNKNOWN`、等待机器人、账本失败 |
| 影响范围 | 影响哪个 NodeJob、分支、设备、物料或下游节点 |
| 证据摘要 | 时间、来源、Command / Job / Resource 身份 |
| 下一步 | 当前允许的动作和完成条件 |

关注项不能只写“运行异常”“节点失败”或“设备离线”。

### 4.3 活动节点集合代替单一当前节点

运行中允许同时存在多个活动节点：

- `running`：实际执行中；
- `waiting`：等待资源、上游或 Claim；
- `attention`：需要用户核对、确认或处置；
- `succeeded`：已完成但可能仍影响下游准入；
- `execution_unknown`：必须进入未知结果流。

活动节点集合按分支和资源分组，而不是按时间轴压成一列。点击某一项后：

1. 当前运行路径聚焦到该节点；
2. 结构视图高亮上游 / 下游关系；
3. 详情面板打开该 NodeJob 的当前 attempt；
4. 可用动作根据 OS 返回的前置条件更新。

## 5. 运行详情的交互层级

### 5.1 固定层：始终可见

运行头部固定展示：

- Task 名称和身份；
- Workflow / Revision；
- 仿真 / 真机；
- Task 生命周期、控制状态、清理状态；
- 当前关注级别；
- OS 返回的控制动作及其生效状态；
- 最近更新时间和数据新鲜度。

头部不展示大量输入 JSON、全部设备列表或全量事件。

### 5.2 主线层：首屏完成调试判断

主线层由三部分组成：

```text
关注栏 | 当前运行路径 / 活动节点集合 | 下一步动作
```

用户不打开任何抽屉也应能判断：

- 当前是否能继续；
- 为什么不能继续；
- 首先要处理什么；
- 如果点击动作，什么事实出现后才算完成。

### 5.3 详情层：选中后展开

选中 NodeJob 后显示：

- 当前 attempt 和历史 attempts；
- input 快照；
- dispatch / Command；
- 设备反馈和物理见证；
- output / returnInfo / feedback；
- 错误、`uncertaintyReason` 和等待原因；
- 资源、Site、账本和结算影响；
- 当前允许动作及前置条件。

不同 `executor_kind` 使用不同字段组，但共享身份、状态、证据和处置框架。

### 5.4 支撑层：按需展开

以下内容默认折叠或侧面展开：

- 完整 DAG；
- Runtime Events / waterfall；
- Timeline / 调度器泳道；
- 原始日志和 Trace；
- 资源完整历史、试剂目录变更历史；
- 运行输入完整 JSON、内部 UUID 和请求指纹。

渐进展开不是隐藏能力。每个支撑面板都要有明确入口，并显示它与当前 Task / NodeJob 的关联身份。

## 6. Run Preparation 的层级

Run Preparation 是一个有顺序的准备工作区，不是工作流编辑器，也不是资源管理页：

```text
1. 工作流修订
2. 本次输入
3. 资源绑定
4. Preflight
5. 提交运行
```

交互规则：

- 当前只突出一个准备阶段，其他阶段显示完成、待处理或过期；
- 修改输入或绑定后，Preflight 标记为过期，禁止沿用旧结论；
- 点击阻断检查项可以定位到具体字段、候选资源或定义要求；
- 资源候选选择只改变 Binding Draft，不直接修改资源事实；
- 提交前显示即将冻结的 Revision、输入、资源绑定、环境和运行模式；
- SubmitRun 结果未知时，冻结草稿和幂等身份，进入“确认是否已创建 Task”的恢复路径。

## 7. 定义和资源的进入规则

### 7.1 从运行进入资源

节点详情中的资源链接只打开当前运行上下文的资源摘要：

```text
当前物料 / 试剂 / 设备
  → 当前 Site、数量、占用、绑定原因、影响节点
  → 查看完整详情
  → 返回原 NodeJob / 运行路径
```

在资源摘要中，维护动作必须明确标注会不会影响当前运行。危险或跨运行操作需要单独确认，不能和查看状态共用一个按钮。

### 7.2 从定义进入运行准备

Definition Revision 的主要动作是 `开始调试`，而不是 `编辑画布`。编辑、复制、发布和版本差异属于高级动作，与运行准备分离。

工作流详情首屏只回答：

- 这是什么版本；
- 需要哪些输入和资源；
- 结构上有哪些分支和子流程；
- 最近一次运行发生了什么；
- 如何开始一次新的调试。

### 7.3 设备动作调试

设备动作可以从资源空间或定义空间开始，但提交后统一进入运行工作区：

```text
设备 / Action
  → 参数和执行前检查
  → 仿真 / 真机确认
  → Task + 单个 NodeJob
  → 与工作流运行相同的关注、证据和处置
```

不能因为入口是设备动作，就显示一套只包含“在线 / 离线 / 成功 / 失败”的独立状态。

## 8. 运行上下文保持规则

下列操作都必须保留当前上下文：

- 运行 → NodeJob 详情；
- NodeJob → 设备 / 物料 / 试剂摘要；
- 运行 → 完整 DAG；
- 运行 → Events / Timeline；
- Preflight → 资源候选；
- 资源维护后返回运行。

至少保留：

```text
taskUuid
workflowRevision
selectedJobUuid
selectedAttempt
activeBranch
currentFilter
scroll / zoom 状态（如适用）
```

如果资源维护或网络刷新导致上下文无法恢复，页面必须明确提示“已返回同一运行，但当前事实已重新读取”，不能静默回到列表首页。

## 9. 信息架构与三条任务流的映射

| 任务流 | 主工作区 | 首屏主线 | 次级内容 |
| --- | --- | --- | --- |
| 从零开始调试 | 调试工作台 → Run Preparation | 当前阶段、阻断检查、下一步提交 | Revision DAG、资源完整详情、历史 |
| 运行中定位 | 运行工作区 | 当前关注栏 → 活动节点集合 → 当前运行路径 | 完整 DAG、Events、Timeline、原始日志 |
| 未知结果处置 | 运行工作区 → NodeJob / Disposition | 未知事实、证据包、影响范围、对账 / 人工动作 | 设备详情、物料历史、Trace、完整事件 |

这三条路径共享运行身份和详情组件，但不共享一个模糊的“调试首页大屏”。

## 10. 第六步的 UI 验收标准

### 主线

- 用户进入系统后能立即选择“开始新的调试”或“继续处理运行”；
- 运行详情首屏不依赖完整 DAG，也能回答当前阻断和下一步动作；
- 工作流、实验室操作和设备动作不会以三张同等优先的调试工作台互相竞争；
- 资源详情从运行进入时保留 Task、NodeJob 和筛选上下文。

### 层级

- 当前事实、影响范围、证据摘要和下一步动作在首屏可见；
- NodeJob 的 input / output / feedback / attempt 在选中后可见；
- 完整拓扑、事件、Trace、历史和原始日志按需展开；
- 每个动作都显示命令提交、生效和完成的区别。

### 真实场景

- S07 中烧杯和粉桶两个分支可以同时观察；
- “等待机器人 Claim”不会显示成设备故障；
- `UNKNOWN` 和物理成功 / Host 账本失败会进入不同的处置入口；
- 投粉节点为什么不能开始可以追溯到具体 Site、物料、Claim 或证据；
- 单样品长流程的资源、库存和清理信息不会把运行主线淹没。

## 11. 第六步完成判定

第六步现在可以判定为完成：

- 已确定调试工作台、运行工作区、定义与版本、资源与现场的职责边界；
- 已明确运行详情的首屏主线是“当前关注 → 当前运行路径 → 下一步动作”，不是完整画布；
- 已规定 NodeJob 详情、证据、完整拓扑、事件和资源历史的渐进展开层级；
- 已定义三条任务流与工作区、首屏主线和次级内容的映射；
- 已给出真实 S07 和单样品流程的 UI 验收标准；
- 已解决“首页四个分类”的风险：路由可以存在，但只有调试主线拥有默认优先级，支撑空间不与运行任务平级竞争。
